# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). While the version is below 1.0, the public API may change between minor versions.

## [0.1.1] - 2026-11-25

### Fixed

- Declare `httpx2` (`>=2.10.0`), which gravitywell imports directly, rather than relying on ClientX to install it.

## [0.1.0] - 2026-11-25

### Added

- `PiHole` and `AsyncPiHole`, clients for a Pi-hole's v6 REST API, with `api.info.version()` for the installed versions of the Pi-hole's components (`GET /api/info/version`). They take the Pi-hole's URL, such as `http://pi.hole`, a required `auth=`, and `verify=` and `transport=`. Each endpoint returns a model of its whole response body, from `gravitywell.models`, which extends `BaseResponse` and so has `took`, the seconds the Pi-hole took to process the request.
- `PiHoleAuth`, for a client's `auth=`, with a password, preferably an application password, or a function that returns it, called at each login, such as to read a secret file that changes. It logs in before the first request (`POST /api/auth`), sends the session in the `X-FTL-SID` header, logs in again once after a 401, and shares one login between concurrent requests. A failed login raises `httpx2.HTTPStatusError` with the login's response. Two-factor authentication isn't supported.
- Closing a client (`close()`, `aclose()`, or leaving its `with` block) logs out of its `PiHoleAuth` session, so it doesn't hold one of the Pi-hole's few sessions until it expires.
- `api.dns.blocking()` and `api.dns.set_blocking()`, to read and change whether the Pi-hole blocks ads and trackers, with an optional timer that switches the status back on its own (`GET` and `POST /api/dns/blocking`). AI tools mark `set_blocking` as destructive and idempotent.
- `api.info.system()`, `host()`, `sensors()`, `ftl()`, `database()` and `metrics()`: the Pi-hole machine's resource use, operating system and temperatures, FTL's database contents, privacy level and resource use, the query database's size, and FTL's DNS cache, reply and DHCP counters (`GET /api/info/...`).
- `api.info.messages()`, `message_count()` and `delete_messages(ids)`: the problems the Pi-hole reports on its diagnosis page, such as invalid regex rules, lists that failed to download or unreachable upstream servers, and deleting them once dealt with (`/api/info/messages`).
- `api.stats.summary()`, totals of the Pi-hole's queries (blocked, forwarded and cached, and by record type, status and reply), clients and blocklists, over the history it keeps, the last 24 hours by default (`GET /api/stats/summary`). The blocklists' last update is a `datetime` in UTC, or `None` when the Pi-hole doesn't know.
- `api.stats.top_domains()` and `api.stats.top_clients()`, the most queried domains and the clients that sent the most queries, ranked by permitted (domains) or all (clients) queries, or by blocked queries with `blocked=True`; `count=` sets how many, 10 by default (`GET /api/stats/top_domains` and `/api/stats/top_clients`). Their totals are `None` when the Pi-hole's privacy level hides the list.
- `api.stats.upstreams()`, `api.stats.query_types()` and `api.stats.recent_blocked()`: where queries went (blocked, cached, or which upstream DNS servers answered, with their response times), queries by record type, and the most recently blocked domains, newest first (`GET /api/stats/upstreams`, `/api/stats/query_types` and `/api/stats/recent_blocked`).
- `api.stats.database`, the same statistics over a time range of the Pi-hole's query database, which keeps queries for 91 days by default: `summary()`, `top_domains()`, `top_clients()`, `upstreams()` and `query_types()` (`GET /api/stats/database/...`). Each takes a `TimeRange`, with a `start` and an `until` that defaults to now, both `datetime`s with a timezone, sent to Pi-hole as Unix seconds.
- `api.history.activity()` and `api.history.clients()`, query counts and each client's query counts over the last 24 hours in 10-minute slots (`GET /api/history` and `/api/history/clients`), and `api.history.database`'s `activity()` and `clients()` over a `TimeRange` (`GET /api/history/database` and `/api/history/database/clients`). Slot times are `datetime`s in UTC.
- `api.search.lists(domain)`, the allow and deny rules and the blocklist and allowlist entries that match a domain, such as to see why it's blocked, with `partial=True` for entries that contain it and `count=` for how many of each kind, 20 by default (`GET /api/search/{domain}`).
- `api.explain_domain()`, `api.explain_client()` and `api.check_health()`, AI tools that each answer in one call what takes several endpoints: why a domain is blocked or allowed, who a client is and which groups it's in, and what's wrong with the Pi-hole, in plain words. `gravitywell-mcp` serves them by default, as `--areas insights`. Version replies now include each component's newest release, as `remote`.
- `gravitywell-mcp`, an MCP server for gravitywell's AI tools, with the `mcp` extra (`pip install "gravitywell[mcp]"`), and `gravitywell.mcp.create_server()` to build it from a client of your own. It serves the read-only tools unless `--allow-writes` or `--allow-destructive` allows more, only the API areas `--areas` names, over stdio or HTTP, and logs out when it stops. It reads its settings from the environment, or a `.env` file `--env-file` names. Each resource is tagged with its area.
- `api.sessions.list()` and `delete()`: the sessions logged in to the Pi-hole's API, to log out ones apps left open (`/api/auth/sessions`). `api.padd.summary()`: the Pi-hole's state in one call, as PADD shows it (`/api/padd`). `api.teleporter.export()` and `restore()`: Teleporter backups, for Python only, not AI tools (`/api/teleporter`).
- `api.config.settings()` and `update()`: read Pi-hole's settings with its own description of each, and change several at once, all or none, within the `dns`, `dhcp`, `ntp`, `resolver`, `database` and `debug` topics, the privacy level, and the statistics' exclusions and history. `api.config.reverse_servers()`, `add_reverse_server()` and `delete_reverse_server()` for conditional forwarding, and `static_leases()`, `add_static_lease()` and `delete_static_lease()` for static DHCP leases.
- `api.config.dns_records()`, `add_dns_record()` and `delete_dns_record()`, `cname_records()`, `add_cname_record()` and `delete_cname_record()`, and `upstreams()` and `set_upstreams()`: the Pi-hole's local DNS and CNAME records and its upstream DNS servers (`/api/config/dns/...`). Changing them with an application password needs the Pi-hole's `webserver.api.app_sudo` setting.
- `api.action.update_gravity()`, `restart_dns()`, `flush_logs()` and `flush_network()` (`/api/action/...`): update gravity from the lists, restart FTL, delete the last 24 hours of queries, and forget the network's devices. A gravity update returns its output as a terminal shows it, and whether it succeeded, which Pi-hole only says inside its output.
- `api.logs.dnsmasq()`, `ftl()` and `webserver()`: the newest lines of the DNS resolver's, FTL's and the web server's logs (`/api/logs/...`), with `next_id` to poll for new lines and `lines` to keep only the newest. Session IDs, which FTL logs with its `debug.api` setting on, read as `<redacted>`.
- `api.network.devices()`, `delete_device()`, `gateway()`, `interfaces()` and `routes()`: the devices the Pi-hole has seen, with their addresses, hostnames and activity, and its machine's gateway, interfaces and routes (`/api/network/...`). `api.dhcp.leases()` and `delete_lease()`: the DHCP server's leases (`/api/dhcp/leases`).
- `api.queries.log()`, the query log, newest first (`GET /api/queries`): filter by a `TimeRange`, domain, client IP or name, and upstream (with `*` wildcards), and by record type, status, reply and DNSSEC status; read the query database with `disk=True`; page with `count`, `start` and `cursor`. Each query's `list_id` is split into `rule_id` and `list_id`. `api.queries.suggestions()` lists values to filter by (`GET /api/queries/suggestions`).
- `api.domains`, the allow and deny rules for domains: `list()`, `get()`, `add()` (one domain or several, reporting which were saved), `update()`, `move()` (to another type or kind), `delete()` and `batch.delete()` (`/api/domains`). AI tools mark adding as safe, and updating, moving and deleting as destructive.
- `api.lists`, the blocklists and allowlists the Pi-hole subscribes to: `list()`, `get()`, `add()` (one URL or several, reporting which were saved), `update()`, `delete()` and `batch.delete()` (`/api/lists`). Each list shows its domain count and how its last download went.
- `api.groups`, the groups of clients that rules and lists apply to: `list()`, `get()`, `add()` (one name or several, reporting which were saved), `update()`, `rename()`, `delete()` and `batch.delete()` (`/api/groups`). `delete()` and `batch.delete()` refuse to delete the Default group, found by its ID even when renamed, with an `ArgumentError`: Pi-hole would re-create it empty, detaching every rule, list and client in it.
- `api.clients`, the clients the Pi-hole recognizes by IP address, subnet, MAC address, hostname or interface, and the groups they're in: `list()`, `get()`, `add()` (one or several, reporting which were saved), `update()`, `delete()`, `batch.delete()`, and `suggestions()` for devices seen but not configured yet (`/api/clients`).
- `gravitywell.PIHOLE_VERSIONS`, the Pi-hole release gravitywell was modeled on and tested against: core v6.6, web v6.6.1 and FTL v6.9, keyed by component as `api.info.version()` names them.
